# ADR-003: Rendering Strategy

**Status:** Implemented  
**Date:** 2026-07-24

## Decision

Use Static Site Generation (SSG) for published pages, with `generateStaticParams()` for case studies.

---

## Context

The portfolio contains:

- Infrequently changing published content.
- No user-specific or real-time data.
- Strong SEO and performance requirements.

---

## Decision

Render published content at build time.

Implementation includes:

- Case studies generated using `generateStaticParams()` and `next-mdx-remote/rsc`.
- Static pages rendered through the default Next.js static rendering pipeline.
- Page metadata generated through `generateMetadata()`.
- Interactive elements implemented as client components only where required.

No server-side rendering (SSR) or client-side content fetching is used.

---

## Rationale

1. Case studies change infrequently, making static generation appropriate.
2. Static HTML improves loading performance.
3. Metadata is available in the initial response for search engines.
4. The deployment model aligns with a static publishing workflow.
5. The project's scale does not justify more complex rendering strategies.

---

## Trade-offs

### Chosen

- Static Site Generation for published content.

### Accepted

- Publishing new content requires rebuilding and redeploying the site.

### Rejected

- Incremental Static Regeneration (ISR), because it adds complexity without meaningful benefit.
- Server-Side Rendering (SSR), because content is static.
- Client-side content fetching, because it reduces SEO effectiveness and delays rendering.

---

## Implementation Notes

- `app/work/[slug]/page.tsx` exports `generateStaticParams()`.
- `app/work/[slug]/page.tsx` exports `generateMetadata()`.
- Case studies are rendered using `next-mdx-remote/rsc`.
- The project uses the standard Next.js static build process.
